# 浇水平台设备身份与持久保存方案
修订日期 2026年10月13日  文档编号 硬件2

本方案完善配置与目标设备的关联、断电保存和运行恢复，并给出生产身份认证的独立实施条件。固件沿用稳定芯片ID和已有BLE契约；开发交付包括编译、USB烧录及真实Flash验证。

## 一 当前身份与保存基础
3.4.0固件通过ESP.getEfuseMac()生成C3-xxxxxxxxxxxx设备ID，同一芯片在正常重启、更新固件和恢复出厂后保持一致。网页核对握手身份，固件要求配置revision递增，BLE接受一个客户端，读写操作串行执行。
设备使用NVS的watercfg/package保存CRC32及完整UTF-8配置，写入后回读字节一致再回复saved:true与revision。启动检查长度、CRC和配置结构。

| 标识 | 用途 |
| --- | --- |
| deviceId | 稳定识别具体ESP32 |
| fwVersion | 固件版本和能力判断，当前3.4.0 |
| configVersion与protocolVersion | 配置结构及协议契约，当前1.0 |
| revision或configRevision | 当前设备的配置更新顺序 |
| 消息id | 请求、分包与回执归属 |
| nonce与confirmationToken | 当前会话的短期认证与操作确认 |
| 知识库version与sourceVersion | 参数生成的数据依据 |

## 三 HW2 01 配置与目标设备关联
网页在页面内存中将生成场景、预览配置、目标deviceId及设备revision关联。未连接时允许预览，发送前通过握手确定目标；切换设备、断开或取消时重新核对身份，身份变化则重新确认场景和目标。
先实施网页目标确认，复用services/device.js和配置页。需要设备端拒绝跨设备写入时，再设计写入封装或版本化目标字段，并同步后端导入白名单、浏览器校验和固件解析。新增字段以端到端读回验证为准。
重连后读取当前revision。过旧配置进入重新生成或显式更新流程；发送结果根据设备的saved:true和revision确认。每台设备的植物、历史、事件和结果按deviceId隔离，迟到响应绑定原会话处理。
多设备使用采用逐台连接、逐台确认和独立结果记录。验收包括A预览后切换B、同型号同revision设备、取消后迟到响应、配置在其他会话更新、重连及恢复出厂。

## 四 公共字段与兼容
传感器事件使用deviceId与稳定sensorKey，通道名采用soil、rain、temperature、humidity和solar。维修换件更新本地校准版本；基准和事件同时关联配置revision。
硬件1的质量、环境范围与时间字段通过版本化契约接入。握手声明能力，网页据此启用操作。新旧配置与固件的兼容行为写入协议和测试，数据、身份与请求分别保留各自标识。

## 五 保存结果的页面规则
收到saved:true且revision匹配，页面显示“已保存”。后续状态刷新失败时保留保存事实，并提示重连检查。
最终回执缺失时显示“保存结果未确认”。重连、重新握手并读回配置，核对目标、revision和内容后更新结果。核对完成前暂停重复写入，防止不确定请求被再次执行。
验收分别模拟传输失败、回执丢失、保存后刷新失败和换设备重连，检查页面事实与设备实际状态一致。

## 六 HW2 02 配置与运行状态持久化
沿用现有单blob格式与CRC校验，将配置、校准、运行检查点和历史分开定义。分包缓存、认证挑战、确认令牌和连接状态属于会话数据，断开或重启时清除；deviceId保持稳定。
启动先关泵，读回有效配置后再检查标定、运行模式和时间条件。读取失败进入未配置或错误状态，给出重新发送或恢复步骤。配置升级和旧格式迁移采用明确的兼容规则。
一次浇水开始前保存尝试状态，完成后记录结果及间隔基准。断电中断的轮次标记为中断或结果未知，恢复时抑制整轮重复执行。时间无法证明最短间隔已满足时进入安全等待，与硬件1共用恢复条件。
历史与事件采用独立有界存储，确定容量、写入节流、掉电损失范围、分区和磨损预算。RTC负责跨深睡状态，完全断电状态依靠持久化记录恢复。

| 断电或错误场景 | 检查结果 |
| --- | --- |
| 正常保存后断电 | 配置内容与revision可读回，身份一致 |
| 收包中断电 | 未完成会话被清理，启动保护生效 |
| NVS写入附近断电 | 记录实际恢复版本、完整性与错误状态 |
| 保存后回执前断电 | 重连读回可确认实际保存结果 |
| 损坏或读取失败 | 进入安全状态，给出恢复步骤 |
| 浇水中断电 | 记录中断，关泵启动并执行间隔保护 |

单blob现状按实际故障注入结果验收；需要保留上一有效版本时，再评估应用层双槽及切换规则。恢复出厂列明配置、校准、日志和检查点的清除范围，并测试稳定身份及会话清理。
本阶段通过条件是：读回结果可解释、损坏数据触发安全状态、未知写入可核对、恢复时保护生效。真实Flash、实际泵状态和主机契约测试分别留档。

## 七 HW2 03 生产身份与链路保护
此项为P2；面向陌生用户提供正式设备授权时，纳入发布准入。当前nonce与公开开发口令的SHA-256挑战用于开发联调，页面按“开发认证”展示。生产认证需建立独立设备凭据与用户权限验证。
先定义设备真实性、控制权限、配置来源和内容保护各自目标，再设计凭据生产写入、验证、失效、替换和维修流程。浏览器使用公开验证材料验证设备证明；生产秘密凭据放在适合的安全存储和发行流程中。
部署侧按HTTPS设计网页与Flask访问，设备侧评估BLE配对、链路保护或应用层保护。分包、CRC、限长、超时和串行请求继续负责传输错误检测与恢复。
新能力由握手声明并验证，界面按验证结果展示。验收覆盖复制ID、独立设备凭据、过期挑战、重放、错误数据及版本兼容，权限失败时停止写入和控制。

## 八 固件交付与实施顺序
先恢复编译环境，验证现有NVS保存与真机读回；再完善HW2 01目标关联；运行检查点随硬件1的控制模块开发；生产身份按独立契约推进。
每次编译记录C3板型、核心与库版本、分区、源文件及二进制哈希。确认USB端口后烧录，读回deviceId、fwVersion、能力和revision，再执行该阶段断电及重连测试。
保留可恢复构建与配置、校准记录。升级和回退检查分区及配置结构兼容；构建清单随实际源码更新。交付包括代码、协议、构建与烧录日志、恢复出厂范围和故障注入记录。

## 九 项目依据
路径相对于Watering-platform根目录。
- esp32-firmware/ble_oled_pairing/ble_oled_pairing.ino：芯片ID、Preferences存储及回读。
- esp32-firmware目录的ble_oled_pairing/include/sws_core.h和docs/ble-protocol.md：revision、会话、确认令牌与回执。
- esp32-firmware目录的README.md、verification.md、build.ps1和tests：构建与验证入口。
- prototype/static/js目录的services/device.js及pages/configure.js：身份、串行发送及结果展示。
- prototype目录的engine/validation.py和README.md：字段过滤、版本、页面临时配置。
