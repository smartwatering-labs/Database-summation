# 浇水平台设备身份与断电保存改进方案
修订日期 2026年10月13日  对应原稿 硬件2

本方案保留原稿关于设备区分、防止误写、配置断电保持和身份可信度的意图。将“一设备一编译”改为稳定设备身份与配置版本管理，并把生产防伪作为独立增强。当前项目通过网页生成JSON参数，经BLE写入设备，不在网页编译或烧录ESP32固件。

## 一 已有能力和标识分工
固件3.4.0已从ESP.getEfuseMac()取得完整芯片MAC并派生 C3-xxxxxxxxxxxx 设备ID。该ID不是每次生成配置时分配的随机号，同一芯片正常重启、更新固件或恢复出厂后应保持一致。它用于识别设备，不能单凭格式或MAC证明产品真伪。

| 标识 | 用途和生命周期 |
| --- | --- |
| deviceId | 稳定设备身份，区分具体ESP32 |
| fwVersion | 固件版本，当前3.4.0，供兼容和能力判断 |
| configVersion与protocolVersion | 配置结构和协议契约版本，当前1.0 |
| revision或configRevision | 设备当前配置新旧顺序，不是全局编号或服务器历史 |
| 业务消息id | 区分一次请求及其分包、回执，不是设备ID |
| nonce与confirmationToken | 当前连接的短期认证挑战和操作确认，不长期保存 |
| 植物库与权重库version | 生成参数的数据依据，与设备身份分别管理 |

已有前端会核对握手设备身份，固件拒绝不递增的配置revision；设备只允许一个BLE客户端，网页将读写串行。上述措施为现有基础，不必从零设计“唯一编译位号”。

## 二 原稿事项处理对照
每次编译分配设备ID改为使用现有稳定deviceId；客制化编译改为当前场景参数生成与型号能力校验。防止批量编译改为防止跨设备误写，不将原稿中的限制与另一份原稿的批量提效要求同时设为目标。
“我司产品真伪”改为待评估的生产设备认证，不据原稿补造公司、商业授权或云端设备登记现状。“同一种植物”的转写不能据此强制所有设备种同一物种；数据一致性按单台设备当前配置及协议解释。

## 三 HW2 01 防止切换设备后误写配置
性质为加强现有交互，建议优先级 P1。保留稳定设备ID，新增配置预览与发送过程中的目标设备确认。项目当前生成配置主要按deviceModel和revision校验，配置结构没有强制绑定targetDeviceId；同型号且版本允许的配置仍可能写入另一台设备。
建议网页在已连接时把目标deviceId、当前revision和生成场景关联在页面内存中。切换设备、断开或取消连接时重新核对目标；若身份变化，停止旧配置直接发送，提示用户重新确认场景及目标。未连接时仍可生成预览，实际发送前再确定设备身份和版本。
最小实施可先做网页侧目标确认，不改变配置结构。若要求固件也拒绝跨设备误写，再设计独立的写入封装或新版本字段。当前后端导入校验会过滤未列出的配置字段，不能仅向JSON追加targetDeviceId就声称端到端绑定已生效。
重连同一设备也要重新握手，读取当前revision。旧revision配置不自动改号重发；让用户重新生成或执行明确的版本更新流程。收到保存回执后依据设备返回的revision展示结果；GATT写入成功不等于NVS保存成功。
验收场景包括A生成后切换B、同型号同revision的两台设备、连接取消后迟到响应、设备在后台更新配置、重新连接及恢复出厂。前端不能把A的植物、历史或写入结果显示为B的数据。
原稿关于批量设备的意图，现阶段只转为逐台连接、逐台确认和隔离数据。自动扫描、并发连接、批量烧录与商业授权不进入本期任务。

## 四 与硬件2之外方案的衔接
传感器事件按deviceId和sensorKey关联。sensorKey首先采用稳定通道名，如soil、rain、temperature、humidity和solar，不要求给每个无独立身份芯片的传感器分配真实序列号。维修换件可在本地校准记录中标识版本。
HW1的环境范围、质量事件和时间字段若写入配置或历史，需要版本化设计；旧固件能力不足时网页应提示并限制操作。设备身份、消息身份和参数数据版本分别校验，不把它们合并成单个“数据库编号”。

## 五 HW2 02 断电保持与恢复验证
性质为验证并完善现有功能，建议优先级 P0。当前配置已经存入NVS的watercfg/package单一blob，内容为CRC32及完整UTF-8配置。固件校验、写入并回读字节一致后才返回saved:true和revision；开机重新检查长度、CRC及配置结构。
这项能力已经有源码，但真实Flash断电保持仍需实物验证。不能把“内存保存”或主机测试的重新构造Endpoint当作断电试验。NVS用于已提交配置；分包缓存、认证nonce、确认令牌和连接状态属于易失会话，断开或重启后清除。
建议分别检验正常保存后断电、收包中断电、写入附近断电、保存后回执前断电以及启动读回失败。记录上电后实际读到的配置、revision和错误状态。当前单blob实现没有显式的应用层双槽回滚，不能承诺断电必定恢复旧版；是否需要双槽，要由故障注入结果和所需可靠性决定。
若网页没有收到最终回执，结果为“未确认”。重连后读取设备配置核对，不自动重新执行写操作。若已收到saved:true，后续状态读取失败仍保持“已保存”事实，并提示重连检查。
无有效配置时保持未配置或错误状态。未来自动浇水固件启动先关泵，不从损坏配置中推测控制参数，也不因恢复失败直接使用激进默认值。读取到有效配置也不代表立即启动LONGRUN，仍需按模式和运行安全条件恢复。
恢复出厂应明确清除用户配置与未来校准、日志等哪些内容；当前实现只体现现有NVS配置清除。稳定芯片ID应保留，认证会话清除。旧零散NVS键与当前package格式不自动迁移，需显式重新发送或设计迁移。
运行历史不能与配置同频刷写NVS。新增采样、异常事件和浇水检查点时，另定义环形容量、写入节奏、磨损预算、掉电损失范围及文件系统恢复行为。RTC仅用于跨深睡状态，不等于完全断电保持。
验收结果应列出每类中断的恢复行为；只有正常配置可读回、身份不变、损坏数据不驱动执行器且未知写入结果可核对，才能称为完成本阶段。

## 六 HW2 03 生产身份认证与传输保护
性质为新增独立方案，建议优先级 P2；若准备面向陌生用户提供正式设备授权，则提升为发布前置。当前SHA-256(nonce加公开开发口令)用于开发联调，不能证明产品来自特定制造方，也不能保证配置保密。Base64只是编码，CRC32只检出传输损坏。
建议先明确要解决的问题：识别原厂设备、验证用户是否有权控制、验证配置来源以及保护链路内容是不同目标。稳定ID可以继续保留，但可信身份需要独立设备凭据或可验证证书，并设计生产写入、验证、失效、替换和维修流程。
不把所有设备共用的生产主密钥放到公开网页JS。若浏览器直接与设备认证，应评估可由公开验证材料验证的设备证明及用户授权机制；具体密码方案另做设计评审和测试。本文件不在没有密钥供应流程的情况下指定AES、RSA或ECC拼装协议。
网站与Flask部署链路使用HTTPS，浏览器与ESP32之间是BLE链路，需要另外确认配对、链路保护或应用层保护。加密不能提高无线信号强度；传输稳定性仍由分包、限长、校验、串行操作、超时和失败恢复承担。
新增安全能力必须由网页和固件共同声明与验证，界面显示“开发认证”或实际安全能力；没有完成验证就不显示“已防伪”或“加密传输”。不把管理员密钥和设备认证凭据混用。
验收分别检验不同设备凭据、被复制的ID、过期挑战、重放、错误或损坏数据以及不支持的新旧版本。源码不能直接包含生产私密凭据，拒绝失败后不进入配置或执行器操作。

## 七 建议顺序与待确定事项
先验证HW2 02的真实断电保存，随后完善HW2 01的目标设备确认。HW2 03按发布范围独立评估，与网页2的安全说明共用一份契约，避免重复实现。
后续需要确定目标绑定是否做到固件端、未知保存结果的交互、旧配置迁移范围、恢复出厂清除范围，以及是否真的需要产品防伪和离线设备授权。原稿未明确的商业目标保持为可选需求，不作为现有事实。

## 八 项目依据
路径相对于项目根目录 Watering-platform。
- esp32-firmware/ble_oled_pairing/ble_oled_pairing.ino：芯片MAC派生ID、Preferences单blob存储与回读。
- esp32-firmware/ble_oled_pairing/include/sws_core.h：revision校验、会话清理、确认令牌及保存回执。
- esp32-firmware/docs/ble-protocol.md、README.md、verification.md：开发认证边界、存储格式和实物待验状态。
- prototype/static/js/services/device.js：身份变化保护、串行读写、保存后状态失败处理。
- prototype/engine/validation.py：配置字段白名单、型号与版本校验。
- prototype/README.md：页面临时配置、无后端个人配置历史、实际功能边界。
