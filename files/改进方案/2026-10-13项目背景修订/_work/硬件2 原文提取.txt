## 一、议题一：ESP32 唯一设备 ID 与客制化编译

1. **唯一设备 ID 分配**
   - 每次编译时，为 ESP32 分配其唯一的设备 ID。
   - 该 ID 作为设备身份标识，用于后续编译、连接和校验。

2. **客制化编译策略**
   - 根据 ESP32 本身的设备 ID 特征，以及该设备所承担的功能，进行客制化编译。
   - 目标是实现“一设备一 ID、一功能一编译”的管理方式。

3. **主要目的**
   - 防止后续用户进行批量编译。
   - 防止多用户同时编译不同设备时产生数据乱串、数据串扰现象。
   - 保证不同设备、不同功能之间的编译数据相互隔离。

4. **与网页端连接及真伪校验**
   - 以设备唯一 ID 作为与网页端的临时性连接标识或连接凭证。
   - 通过该唯一 ID 验证产品真伪。
   - 防止第三方劣质产品，或不相关的 ESP32 内容作为潜在干扰源，干扰公司正常编译流程。
   - 同时避免无效编译占用资源，减少潜在算力浪费。

---

## 二、议题二：ESP32 关机不丢包与长期数据保持

1. **平时数据保持**
   - 除非明确接收到编译指令，否则设备在平时状态下，一旦写入固定数据包，就保持该数据化形态。
   - 即固定数据包写入后，不随意变更或丢失。

2. **断电后数据保持**
   - 即使在断电之后，相关数据仍记录在存储中，作为长期数据保存。
   - 原文称“内存”，建议后续明确为非易失存储介质，如 NVS、Flash 或 EEPROM。

3. **长期唯一 ID 记录**
   - 要求记录设备本身的长期唯一 ID。
   - 该 ID 用于保证设备长期有效性，并作为后续识别、校验和连接的基础。

4. **数据库与协议一致性**
   - 要求保持同一个数据库、同一种“植物”（此处疑似语音识别误差，可能为“协议”“固件”或“植入方式”，需确认）。
   - 目的是防止在极端特殊情况下，设备断电再自重启后发生丢包。
   - 通过统一数据库和协议策略，提高异常重启后的数据恢复能力。

---

## 三、初步结论与决议

1. 确认采用唯一设备 ID 管理 ESP32 的编译、网页连接和真伪校验。
2. 编译过程需结合设备 ID 与功能角色，实行客制化编译，避免批量编译和数据串扰。
3. 固定数据包与长期唯一 ID 需具备断电保持能力，确保关机不丢包。
4. 数据库与协议需保持统一，具体统一范围和技术实现待进一步确认。
5. 本议题形成初步方向，后续需输出详细技术方案并评审。
