## 项目目标与架构约束

- 项目是 Smart Watering System：Flask 后端生成临时配置，浏览器通过 BLE 把配置交给 ESP32；ESP32 收到后独立运行。
- ESP32 应独立采样、判断、控制执行器并保留配置；自动浇水不能依赖网页持续打开。
- 不恢复 ESP32 本地网页、SoftAP 或设备 HTTP 服务。网页与硬件的当前链路是后端配置生成 → 浏览器 BLE → ESP32 自治运行。
- 网站现有本地地址曾为 `http://127.0.0.1:5000`。
- 用户希望持续推进至计划完成，尽量把测试集中到工作尾声；但用户刚刚明确将本轮剩余硬件任务推迟到明天。
- 准确区分已实现的软件行为、已在桌面板验证的行为、真实传感器/泵/舵机尚未验证的行为；不以虚构标定值消除硬件的“请先完成标定”状态。

接板后已完成的具体修复：

1. COM7 上真实启动时 BLE 控制器崩溃。根据 ELF 解码定位 NimBLE-Arduino 2.3.6 与 ESP32 Arduino core 3.3.10 的兼容问题；构建依赖改用/要求 NimBLE-Arduino ≥2.4.0，代码检查 BLE 初始化并记录状态，移除不合适的旧服务启动调用。已安装版本 2.5.1，并重新构建和烧录。
2. 设备日志存储未就绪时，固件每次 tick 都重复写失败日志，造成串口输出拥塞，拖慢 BLE。改成每分钟尝试一次，并在失败后关闭该日志路径；已重新烧录，真实 BLE 连接随之稳定。
3. 浏览器对不同 BLE 阶段显示具体超时原因；配置写入超时仍要求先读回再决定是否重试，避免未知写入状态下重复操作。
4. 前端后台轮询改为不占用用户操作锁；路由更新保留设备操作区 DOM 和当前选择；“从设备读取”完成后自动切到配置预览，并呈现/导出设备配置。已增加相应测试，上一轮记录为协议 JS 23 项与 Edge 业务流程通过。
5. 日志分区已先做原始备份，再只初始化日志格式；配置和 NVS 未清除。日志分区备份：`.tools/device-backups/C3-54dee69205d4-littlefs-before-initialization.bin`，SHA-256 `3CF4E5A0597DD20F5A6F7B56607F7BA795DE600E159F06A7189F7A990F376B46`。串口格式化返回 `LOGS_READY`。
6. 为该设备首次写入设备级认证密钥，返回 `AUTH_PROVISIONED`。认证密钥文件位于 `esp32-firmware/credentials/C3-54dee69205d4-owner.json`，文件被 Git 忽略。文件包含秘密，不得把其内容、密钥、HMAC 或 nonce 放进交接文本或日志。
7. 使用该密钥完成桌面 BLE 客户端的互认证和签名通信：握手、认证、签名状态读取、时间同步、停止、读配置、事件和状态复读均通过。读回为辣椒 R1，logStorageReady=true，calibrationReady=false；时间同步只对当次上电会话有效。
8. BLE 协商 MTU 的吞吐优化已经编译并烧录：通知发送容量使用实际协商 MTU（上限 244 字节）。上一轮真实测得 MTU 256；通知单次上限 244 字节，握手约 0.72 秒、认证约 1.247 秒、签名状态读取约 5.824 秒、配置读取约 5.996 秒。
